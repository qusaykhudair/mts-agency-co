# MTS Agency + MTS Store

موقع **MTS Agency** مع **متجر اشتراكات رقمية** متكامل (ChatGPT، Claude، Canva، CapCut Pro، Gemini، Netflix…) يشمل:

- **صفحة رئيسية للوكالة والمتجر** على `/`: الاشتراكات الأكثر طلباً، خدمات الوكالة، طريقة الشراء، العملاء والأسئلة الشائعة.
- **طلبات خدمات MTS Agency** (تصميم، برمجة، تسويق، إنتاج مرئي…): يطلب العميل الخدمة بتفاصيلها وملفاتها، يستلمها **منفذ الخدمات** أو يسندها المدير، تتم المراسلة على الطلب، ويُسلَّم العمل بروابط وملفات داخل المنصة ليعتمده العميل أو يطلب تعديلات.
- واجهة متجر احترافية (الرئيسية، الأقسام، المنصات، صفحة المنتج بالباقات والخصومات والعدّاد، البحث الفوري، الوضع الليلي، متوافقة مع الجوال).
- تسجيل دخول يدوي بالبريد وكلمة المرور **أو عبر Google**، مع **رقم واتساب إلزامي واختيار رمز الدولة** (يُطلب من مستخدمي Google في خطوة «إكمال البيانات»).
- إتمام الطلب بالتحويل: بنك فلسطين، جوال باي، بال باي (عبر iBURAQ إلى الآيبان)، فودافون كاش — تظهر تفاصيل الحساب والمبلغ بعملة كل طريقة، ثم يرفق المشتري اسمه ورقم الحساب المحوَّل منه وصورة الإيصال.
- **لوحة المشتري**: الطلبات ومراحلها، بيانات الاشتراك المسلَّمة (نسخ/إظهار)، الاشتراكات النشطة، طلبات الخدمات، الإشعارات، الملف الشخصي، طلب الانضمام كبائع.
- **لوحة منفذ الخدمات** (`/provider`): الطلبات المتاحة للاستلام، الطلبات قيد العمل، المراسلة، الملاحظات الداخلية والتسليم.
- **لوحة البائع/المدير**: مراجعة الإيصالات، تأكيد أو رفض الدفع مع السبب، تسليم بيانات الاشتراك بقوالب جاهزة، مراسلة العميل عبر واتساب برسائل جاهزة، المنتجات والباقات، المنصات، الأقسام، طرق الدفع، أسعار الصرف، المستخدمون والصلاحيات، طلبات البائعين، التقييمات، الإعدادات.

## التشغيل على جهازك

المتطلبات: **Node.js 22.13 أو أحدث** (لا حاجة لقاعدة بيانات خارجية — يستخدم SQLite المدمجة في Node).

```bash
npm install
```

انسخ ملف الإعدادات وعدّل القيم (البريد وكلمة مرور المدير):

```bash
cp .env.example .env
```

```bash
npm start
```

ثم افتح:

| الصفحة | الرابط |
|---|---|
| موقع الوكالة | http://localhost:3000 |
| المتجر | http://localhost:3000/store |
| لوحة البائع/المدير | http://localhost:3000/seller |
| لوحة المشتري | http://localhost:3000/account |

### حساب المدير

يُنشأ تلقائياً عند أول تشغيل باستخدام `ADMIN_EMAIL` و `ADMIN_PASSWORD` من ملف `.env`.
إذا لم تحدد كلمة مرور، تُنشأ كلمة مرور عشوائية وتُحفظ في `data/admin-initial-password.txt`.
بعد الدخول غيّر كلمة المرور من «الملف الشخصي».

### المنتجات التجريبية

عند أول تشغيل تُضاف أقسام و30 منصة وحوالي 26 منتجاً **كأمثلة** (الأسعار بالدولار تقريبية). عدّلها أو احذفها من لوحة البائع ← المنتجات.
لإيقاف إضافتها في تثبيت جديد ضع `SEED_DEMO=false`.
لحذف كل البيانات والبدء من جديد:

```bash
npm run reset-db -- --yes
```

## مسار الطلب

1. المشتري يختار الاشتراك والباقة والكمية ← «اشترِ الآن» (يُطلب تسجيل الدخول).
2. يختار طريقة الدفع فتظهر تفاصيل الحساب (رقم الحساب/الآيبان/رقم المحفظة واسم المستفيد) والمبلغ بعملة الطريقة مع أزرار نسخ.
3. يحوّل المبلغ ثم يدخل **اسم المحوِّل** و**رقم الحساب المحوَّل منه** ويرفع **صورة الإيصال** (صورة أو PDF حتى 8MB) ← يُنشأ الطلب بحالة «بانتظار مراجعة الدفع» ويصل إشعار للمدير/البائع.
4. المدير/البائع يراجع الإيصال: **تأكيد الدفع** أو **رفض** مع ذكر السبب (يستطيع المشتري إعادة رفع إيصال صحيح من صفحة الطلب).
5. المدير/البائع يسلّم **بيانات الاشتراك** (حقول مثل البريد وكلمة المرور أو كود/رابط التفعيل + تعليمات + تاريخ الانتهاء) ← تظهر للمشتري في صفحة طلبه مع إشعار فوري، ويمكن إبلاغه عبر واتساب بزر واحد.
6. المشتري يؤكد الاستلام ويقيّم المنتج (أو يكتمل الطلب تلقائياً بعد 3 أيام).

صور الإيصالات **خاصة**: لا يراها إلا صاحب الطلب والمدير وبائع المنتج.

## طلبات الخدمات

1. العميل يختار الخدمة من **خدماتنا** (`/services`) ويكتب عنوان الطلب وتفاصيله، والميزانية والموعد (اختياريان)، وروابط مرجعية، ويرفق ملفات (حتى 6 ملفات، 25MB للملف: صور، PDF، Office، ZIP/RAR، PSD، فيديو وصوت).
2. يصل إشعار للمدير ولكل **منفذي الخدمات**؛ يستلم المنفذ الطلب من «طلبات متاحة» أو يسنده المدير لمنفذ محدد (ويمكنه تغييره لاحقاً).
3. المراسلة بين العميل والمنفذ على صفحة الطلب مع المرفقات، وللفريق **ملاحظات داخلية** لا يراها العميل.
4. المنفذ يرسل **التسليم**: روابط (Google Drive، Figma…) و/أو ملفات مع ملاحظات ← يتحول الطلب إلى «تم التسليم» ويصل إشعار للعميل.
5. العميل **يعتمد التسليم** أو **يطلب تعديلات**؛ ويُغلق الطلب تلقائياً بعد 7 أيام من التسليم إن لم يرد (قابلة للتعديل من الإعدادات).

يلغي العميل طلبه فقط قبل بدء العمل، ويلغي المدير أي طلب مفتوح مع ذكر السبب. الملفات خاصة: لا يفتحها إلا العميل والمدير والمنفذ المسؤول. الخدمات نفسها تُدار من **لوحة الإدارة ← الخدمات**.

### الصلاحيات

- **المدير** يدير كل شيء. **البائع** يدير منتجاته وطلباتها فقط، ولا يستطيع أبداً إدارة طلب اشتراه بنفسه.
- **منفذ الخدمات**: يرى الطلبات الجديدة المتاحة والطلبات المسندة إليه فقط ويعمل عليها ويسلّمها. يُعيَّن من **المستخدمون ← الصلاحيات ← منفذ خدمات**، ولا يمكن سحب الصلاحية منه وهو مسؤول عن طلب مفتوح قبل إسناده لغيره.
- افتراضياً يستطيع البائع تأكيد الدفع أو رفضه لطلبات منتجاته. لأن المبالغ تصل إلى حسابات المتجر، يمكنك قصر ذلك على المدير من **إعدادات المتجر ← السماح للبائعين بتأكيد أو رفض الدفع**؛ عندها يؤكد المدير الدفع ويصل للبائع إشعار بأن الطلب جاهز للتسليم.
- إذا أنشأ شخص حساباً بالبريد ثم سجّل صاحب البريد الحقيقي الدخول عبر Google بنفس البريد، يُنقل الحساب لصاحب Google وتُمسح كلمة المرور ورقم الواتساب القديمان ويُطلب منه إدخال رقمه (حماية من انتحال البريد). لا يُرقّى أي حساب إلى مدير تلقائياً عند التشغيل.

## حسابات البائعين والعمولة

كلها في **لوحة الإدارة ← الحسابات**، والبائع يرى حساباته في **أرباحي وحساباتي**.

- **العمولة**: تأخذ MTS نسبة من كل عملية بيع لمنتجات البائعين، 20% من سعر البيع افتراضيا. النسبة وطريقة حسابها (من سعر البيع كاملا أو من الربح فقط) في **الحسابات ← العمولة والاشتراك**. كل طلب يحفظ العمولة التي بيع بها، فالنسبة الجديدة تطبق على الطلبات القادمة فقط. منتجات المدير تابعة لـ MTS نفسها ولا عمولة عليها.
- **تسعير الباقات**: البائع يكتب السعر الأصلي وربحه، فيظهر سعر البيع (مجموعهما) مع عمولة MTS وما يصله وصافي ربحه، وما يعادل السعر بالشيكل والجنيه. الباقات القديمة تبقى بسعرها حتى يحدد البائع سعرها الأصلي.
- **الأرصدة**: حصة البائع (سعر البيع ناقص العمولة) تدخل رصيده عند اكتمال الطلب، وقبلها تظهر «قيد الانتظار». المستحق للبائع = الطلبات المكتملة ناقص ما حولناه له ناقص الاشتراكات المخصومة من رصيده. سجل كل تحويل للبائع من صفحة حسابه.
- **المسترجعات**: من صفحة أي طلب مدفوع يضغط المدير «إلغاء واسترجاع المبلغ». الطلب المسترجع يخرج من المبيعات ومن أرباح البائع. إذا ألغى البائع طلبا مدفوعا يحسب مسترجعا ويصل للمدير تنبيه بإعادة المبلغ للعميل.
- **اشتراك البائع**: 5$ شهريا (القيمة والعملة قابلة للتعديل)، ويبدأ من يوم الموافقة على البائع. يدفعه البائع بإيصال تحويل يراجعه المدير، أو من رصيده مباشرة، أو يسجله المدير بنفسه (نقدا، تحويل، خصم من الرصيد، إعفاء). بعد انتهاء الشهر مهلة 3 أيام، ثم تغلق لوحة البائع وتختفي منتجاته من المتجر حتى يدفع، وتعود فور تأكيد الدفع. الإغلاق التلقائي يمكن إيقافه، وتصل للبائع تذكيرات قبل الانتهاء وعنده.
- **التقارير والتصدير**: فلتر يومي أو أسبوعي أو شهري أو فترة محددة (الأسبوع يبدأ السبت بتوقيت القاهرة)، والمبالغ بالدولار أو الشيكل أو الجنيه. زر **تصدير** ينزل ملف Excel فيه الملخص والمبيعات والمسترجعات والتحويلات، أو CSV للمبيعات. البائع يصدر حساباته فقط.
- **التسجيل كبائع**: يفتح ويغلق من **طلبات البائعين**، مع وقت إغلاق تلقائي اختياري ورسالة تظهر وقت الإغلاق.

## الفواتير

من **لوحة الإدارة ← الفواتير**.

- **الرقم**: بالشكل `MTS-2026-0001`، من عداد لكل سنة إصدار يزيد ولا ينقص. الرقم ثابت عند التعديل ولا يعطى لفاتورة أخرى حتى بعد الحذف. البادئة تتغير من إعدادات الفاتورة وتطبق على الفواتير الجديدة فقط.
- **المحرر**: النموذج في جانب ومعاينة الورقة المطبوعة في الجانب الآخر، وفوق بعضهما على الجوال. المتبقي والحالة (مدفوعة، مدفوعة جزئيا، غير مدفوعة) يحسبهما الخادم ولا يكتبان يدويا. زر «مدفوعة بالكامل» يجعل المدفوع يتبع الإجمالي، وأي دفعة جزئية لا تتغير عند تعديل الإجمالي. طريقة التحويل وتاريخه مطلوبان فقط عند وجود دفعة، ولا تطبع بيانات التحويل في فاتورة غير مدفوعة.
- **الطباعة وحفظ PDF**: صفحة A4 واحدة دائما، تطبع فيها الفاتورة وحدها بألوانها في الوضع الفاتح والداكن، واسم ملف PDF هو رقم الفاتورة واسم العميل. إذا طال النص تصغر الخطوط درجة أو درجتين، وإن بقي أطول من الصفحة يظهر تنبيه في المحرر. زر الطباعة في القائمة يفتح الفاتورة وحدها ويطبعها.
- **إعدادات الفاتورة**: الاسم في الرأس والسطر الوصفي والنص الختامي (بالعربية والإنجليزية)، والبريد وواتساب بالصيغة الدولية والموقع. تؤخذ مبدئيا من بيانات المتجر.
- **القائمة**: بحث في الرقم والاسم والطريقة والغرض واسم الدولة بالعربية والإنجليزية، يوحد أ/إ/آ وى/ي وة/ه والأرقام الهندية. فلاتر بالخدمة والعملة والحالة والدولة والفترة (بتاريخ التحويل، أو تاريخ الإصدار إن لم يوجد تحويل)، وإجماليات لكل عملة.
- **الواجهة البرمجية** (جلسة المدير وحماية CSRF): `GET /seller/api/invoices` بالفلاتر `q, service, currency, status, country, from, to, page, per_page`، و`GET /seller/api/invoices/suggestions`، و`GET|PUT /seller/api/invoices/settings`، و`POST /seller/api/invoices`، و`GET|PUT|DELETE /seller/api/invoices/:id`. المبالغ بالوحدة الكاملة (1500.5)، وكل استجابة فيها `status` و`remaining`. أخطاء التحقق تعود بالرمز 422 ومعها `errors` باسم كل حقل.
- **النسخ الاحتياطي**: الفواتير في قاعدة البيانات نفسها (`data/store.db`)، فتدخل في نسخ مجلد `data/`.

## تعديل محتوى الصفحة الرئيسية

- المنتجات والعروض والأسعار وطرق الدفع في الصفحة الرئيسية تُقرأ مباشرة من المتجر، فأي تعديل من لوحة البائع يظهر فوراً. يظهر «عرض لفترة محدودة» تلقائياً لأكبر خصم فيه عدّاد انتهاء.
- خدمات الوكالة تُدار من **لوحة الإدارة ← الخدمات** وتظهر في الصفحة الرئيسية وصفحة «خدماتنا». قائمة العملاء موجودة في `src/lib/content.js`، وشعاراتهم في `public/img/clients/` (صور WebP مربّعة).
- قسم آراء المشترين يظهر تلقائياً بعد وجود 3 تقييمات حقيقية على الأقل.

## طرق الدفع والعملات

- طرق الدفع الأربع مضافة مسبقاً ويمكن تعديل كل تفاصيلها (الأرقام، الأسماء، التعليمات، العملة، الشعار) من **لوحة البائع ← طرق الدفع**.
- الأسعار محفوظة بالعملة الأساسية (الدولار افتراضياً)، وتُحوَّل للشيكل والجنيه حسب **أسعار الصرف** التي تحددها من **لوحة البائع ← العملات** (القيم المبدئية: 1$ = 3.10₪ و 53 ج.م — حدّثها حسب السوق). يُقرَّب المبلغ المطلوب للأعلى ويُحفظ مع الطلب، فلا يتأثر الطلب القديم بتغيير السعر لاحقاً.
- يمكن تغيير العملة الأساسية (مثلاً إلى الشيكل) وسيتم تحويل جميع أسعار المنتجات تلقائياً.

## تفعيل تسجيل الدخول عبر Google

1. ادخل إلى [Google Cloud Console ← Credentials](https://console.cloud.google.com/apis/credentials) وأنشئ مشروعاً.
2. اضبط **OAuth consent screen** (اسم التطبيق والبريد) ثم **Publish app** حتى يستطيع الجميع الدخول.
3. أنشئ **OAuth client ID** من نوع **Web application**.
4. في **Authorized JavaScript origins** أضف رابط الموقع فقط (بدون أي مسار في آخره):
   - `https://mts-agency-co-production.up.railway.app`
   - `http://localhost:3000` (للتجربة على جهازك)
5. (اختياري) في **Authorized redirect URIs** أضف رابط الرجوع، ويُستخدم فقط إذا منع المتصفح النافذة المنبثقة:
   - `https://mts-agency-co-production.up.railway.app/auth/google/callback`
6. ضع الـ Client ID في `GOOGLE_CLIENT_ID` (على Railway في Variables، وعلى جهازك في `.env`) أو من **لوحة الإدارة ← الإعدادات**. لا يحتاج الموقع الـ Client secret.

زر Google من تصميم المتجر نفسه (يتناسب مع الوضعين الفاتح والداكن) ويفتح نافذة Google لاختيار الحساب. يتحقق الخادم مع Google من أن الرمز صادر لهذا الموقع تحديداً، وإذا سجّل شخص عبر Google لأول مرة يُطلب منه إدخال رقم الواتساب. إذا لم تُفتح النافذة ينتقل الزائر لصفحة Google ثم يعود (مع رمز لمرة واحدة state/nonce يمنع التلاعب).

## تأكيد البريد الإلكتروني (كود من 6 أرقام)

من يسجل بالبريد وكلمة المرور يصله كود من 6 أرقام على بريده، ولا يستخدم المتجر قبل أن يكتبه في صفحة «تأكيد بريدك».

- الكود صالح 15 دقيقة ولمرة واحدة، ويتوقف بعد 5 محاولات خاطئة. لا يحفظ الموقع الكود نفسه، بل بصمته فقط.
- كود جديد كل دقيقة على الأكثر، و5 أكواد في الساعة كحد أقصى.
- من كتب بريده خطأ يصححه من صفحة التأكيد، فيصله الكود على البريد الجديد.
- من يدخل بحساب Google يعتبر بريده مؤكدا، لأن Google تحققت منه. والحسابات التي سبقت هذه الميزة تعتبر مؤكدة.
- يستطيع المدير تأكيد بريد عميل يدويا من صفحته في «المستخدمون» إن لم يصله الكود.
- تأكيد البريد لا يعمل إلا بعد ضبط الإرسال. وقبل ذلك يبقى التسجيل كما كان، ويظهر في `/healthz` أن `mail` قيمته `off`.

### ضبط الإرسال عبر Gmail API (يعمل على كل خطط Railway)

Railway يمنع الإرسال عبر SMTP في خطط Free وTrial وHobby، لذلك يرسل الموقع عبر Gmail API من حسابك على Gmail.

1. في [Google Cloud Console](https://console.cloud.google.com/apis/library/gmail.googleapis.com) فعل **Gmail API** في مشروعك (زر Enable). لا تتخطى هذه الخطوة: بدونها يرفض Google كل رسالة ولا يصل أي كود، مع أن تسجيل الدخول إلى Gmail ينجح.
2. من **Google Auth Platform ← Clients** أنشئ Client من نوع **Desktop app**.
3. ضع في ملف `.env`: `GMAIL_CLIENT_ID` و`GMAIL_CLIENT_SECRET`، وفي `MAIL_FROM` بريد Gmail الذي سترسل منه.
4. شغل `npm run gmail-auth` ووافق في المتصفح بالحساب نفسه. يحفظ الأمر `GMAIL_REFRESH_TOKEN` في `.env` دون أن يعرضه على الشاشة. إن ظهرت رسالة أن Google لم يتحقق من التطبيق فاختر Advanced ثم المتابعة، لأنه تطبيقك أنت.
5. جرب الإرسال: `npm run mail-test -- بريدك@gmail.com`.
6. انسخ القيم الأربع (`GMAIL_CLIENT_ID` و`GMAIL_CLIENT_SECRET` و`GMAIL_REFRESH_TOKEN` و`MAIL_FROM`) إلى **Variables** في Railway.

مهم: اجعل حالة التطبيق في **Audience** «In production»، لأن Google تلغي رمز التحديث بعد 7 أيام في وضع الاختبار. وحد Gmail العادي نحو 500 رسالة في اليوم.

بديل: SMTP بكلمة مرور تطبيق من Gmail (`SMTP_HOST=smtp.gmail.com` و`SMTP_PORT=465` و`SMTP_USER` و`SMTP_PASS` و`MAIL_FROM`)، ويعمل على جهازك وعلى خطة Pro في Railway. وللمعاينة المحلية دون إرسال: `MAIL_TRANSPORT=outbox` يحفظ الرسائل في `data/outbox`.

عند التشغيل يفحص الموقع أن الإرسال ممكن فعلا، ولا يطلب الكود من العملاء إلا بعد نجاح الفحص. مع Gmail يطلب الفحص من Gmail إرسال رسالة فارغة، فيرفضها لأنها فارغة دون أن يرسل شيئا، ولا يصل إلى هذا الرفض إلا إذا قبل الرمز وصلاحية الإرسال ووجد Gmail API مفعلة. إن فشل الفحص، أو فشل إرسال كود بسبب الإعدادات، يتوقف طلب الكود فورا ويبقى التسجيل يعمل كالمعتاد، ويعيد الموقع الفحص كل 5 دقائق (وكل ساعة ما دام البريد يعمل). وبعد أي تشغيل جديد ينتظر التسجيل نتيجة الفحص الأول بضع ثوان، فلا يدخل أحد بلا كود لأن الفحص لم ينته بعد.

في **لوحة الإدارة ← الإعدادات** بطاقة «بريد أكواد التأكيد»: حالة البريد، وسبب التوقف وطريقة إصلاحه، وزر «افحص الآن»، ورسالة تجربة بنفس شكل رسالة الكود، وآخر الرسائل التي أرسلها المتجر ونتيجة كل منها (تحفظ 90 يوما). وما دام البريد متوقفا يظهر تنبيه في الصفحة الرئيسية للوحة الإدارة.

تعرف الحالة أيضا من `/healthz`:

| قيمة `mail` | معناها |
|---|---|
| `smtp` أو `gmail` | الإرسال يعمل وتأكيد البريد مفعل |
| `smtp-unreachable` أو `gmail-unreachable` | الإرسال لا يعمل، فتأكيد البريد متوقف (السبب في لوحة الإدارة) |
| `smtp-checking` أو `gmail-checking` | الموقع يتحقق الآن (ثوان بعد التشغيل) |
| `off` | لم تضبط بيانات البريد بعد |

## النشر على الإنترنت

المتجر يحتاج خادم Node.js (لن يعمل على GitHub Pages لأنها تستضيف ملفات ثابتة فقط).

> **رابط Vercel القديم:** الملف `vercel.json` يحوّل كل زوار `mts-agency-co.vercel.app` إلى المتجر على Railway (`mts-agency-co-production.up.railway.app`) مع الحفاظ على المسار. إذا تغيّر رابط المتجر (مثلاً بعد ربط دومين خاص) عدّل الرابط داخل `vercel.json`.
>
> **فحص الحالة:** الرابط `/healthz` يعرض `storage: persistent` عندما تكون البيانات محفوظة على قرص دائم.

**الخيار 1 — خادم VPS (موصى به):**

```bash
npm install --omit=dev
```

```bash
NODE_ENV=production pm2 start server.js --name mts-store --node-args="--disable-warning=ExperimentalWarning"
```

ثم اجعل Nginx يمرّر الطلبات إلى المنفذ 3000 مع شهادة SSL (Let's Encrypt)، واضبط في `.env`:
`NODE_ENV=production` و `TRUST_PROXY=1` و `APP_URL=https://your-domain.com`.

**الخيار 2 — Railway (المستخدم حالياً):** خدمة من مستودع GitHub تُعاد نشرها تلقائياً مع كل رفع على `main`. المتجر يتعرّف على Railway تلقائياً (وضع الإنتاج، البروكسي، الرابط العام)، والمطلوب منك فقط:

1. **أضف Volume للخدمة** (Service ← Volumes، أي مسار مثل `/data`). يحفظ المتجر عليه قاعدة البيانات والإيصالات تلقائياً. بدونه تُحذف الطلبات والحسابات عند كل إعادة نشر، وتظهر لك رسالة تحذير في لوحة المدير.
2. أضف في **Variables**: `ADMIN_EMAIL` و `ADMIN_PASSWORD`. يُنشأ بهما حساب المدير عند أول تشغيل، وإن كان الحساب أُنشئ قبلها ولم يُستخدم بعد فتُطبَّق كلمة المرور عليه في النشر التالي.
3. إن ربطت دوميناً خاصاً بالخدمة أضف `APP_URL=https://your-domain.com`.

**نسيت كلمة مرور المدير أو لا تستطيع الدخول؟** أضف المتغير `ADMIN_RESET_PASSWORD` بكلمة المرور الجديدة (8 أحرف على الأقل) مع `ADMIN_EMAIL`، ثم Deploy وسجّل الدخول بهما — يصبح هذا الحساب مديراً حتى لو كان حساب عميل عادياً — **واحذف المتغير بعدها مباشرة**.

**Render:** نفس الفكرة مع Persistent Disk، واجعل `DATA_DIR` و `UPLOAD_DIR` يشيران إليه.

**النسخ الاحتياطي:** انسخ مجلدي `data/` و `uploads/` دورياً — فيهما كل البيانات والإيصالات.
